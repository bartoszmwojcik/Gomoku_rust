## 2. Administrator identity and the gate

### 2.1 Decision (`isAdminSession`)
1. Resolve the session user as everywhere (`current_user`; any failure incl. DB down is "no user").
2. Administrator iff `user.email_verified_at` is not null AND `is_installation_admin(user.email, config.admin_email)` (already in `validators.rs`: both sides `normalize_email`; no configured address = nobody).
3. Otherwise emit the security event `admin_denied` (no account, no address, no fields: `{"event":"security.admin_denied","ts":ISO}`, Node: one `console.warn` JSON line on stderr; Rust: `tracing::warn!(event = "security.admin_denied")`), and treat the caller as a non-admin. Nothing is logged for the administrator.
4. The role is NEVER stored; changing `ADMIN_EMAIL` and restarting moves the role. The administrator account is created/taken over only by `gomoku-admin create` (F2d), cannot be deleted (`403 ADMIN_ACCOUNT_PROTECTED`), nobody registers with / changes e-mail to that address (all done in F2).

### 2.2 Two gates, one decision
| Gate | Used by | Denial |
| --- | --- | --- |
| `require_admin` (pages) | `/backend`, `/show`, `/show/{id}` | the app's 404 page, exactly what an unknown path returns (status 404, same body, no `Set-Cookie`, no redirect, no `Location`). |
| `require_admin_api` | `/api/show`, `/api/show/preflight`, `/api/show/{id}`, `/api/show/{id}/end` | `404` with envelope `{"ok":false,"error":{"code":"NOT_FOUND","message":"Nie znaleziono partii."}}` (the answer for a game that does not exist). NOT 401/403. |

**Ordering requirement (Rust-specific, important):** in Node the gate runs BEFORE the CSRF check, so a non-admin POST gets the 404 whatever headers it sends. In `app.rs` CSRF is a layer over the whole `/api` router and would answer `403` first: mount `/api/show*` in a router that applies the admin gate layer FIRST and the `csrf` layer second (or outside the `csrf` layer, calling `csrf` inside after the gate). A test must send a POST without `Origin` as a non-admin and expect 404, and as the admin without `Origin` expect the CSRF 403.

Guard tests to port (as Rust tests scanning the source or the route table): every `/backend` and `/show*` page handler calls `require_admin` first; every `/api/show*` route is mounted behind the admin gate; the `/backend` group registers ONLY `GET` routes (the panel is read only: no POST/PUT/DELETE, no actions; Node: `findWriters` must be empty). `/show` is the single place where the administrator writes (create and end a show).

## 4. Pair counters and finished-games statistics

### 4.1 Table (already in Rust migration `0005`)
`game_pair_counters(day date, kind_a varchar(16), kind_b varchar(16), finished_count int default 0, PK (day, kind_a, kind_b), CHECK kind_a <= kind_b, CHECK finished_count >= 0)`. No foreign keys; never cleaned up (the cleanup rules do not touch it), survives account deletion.

### 4.2 What is counted
`record_finished(conn, game_id)` is called by EVERY finish path (five, draw, timeout, resignation, points, lazy timeout settlement), in the same transaction as the `UPDATE ... status='finished'` that returned a row, so the count is +1 exactly once and rolls back with the finish. One statement:
```sql
insert into game_pair_counters (day, kind_a, kind_b, finished_count)
select (g.finished_at at time zone 'Europe/Warsaw')::date, k.kind_a, k.kind_b, 1
from games g join (select game_id, min(kind) as kind_a, max(kind) as kind_b
                   from game_players where game_id = $1 group by game_id) k on k.game_id = g.id
where g.id = $1 and g.status = 'finished' and g.origin <> 'show'      -- <<< F8 adds the show exclusion
on conflict (day, kind_a, kind_b) do update set finished_count = game_pair_counters.finished_count + 1
```
`kind` = participant kind of the two seats (`account`, `guest`, `agent`, `bot`), alphabetical min/max, so the stored pair is e.g. `account/agent`, `agent/guest`, `account/bot`, `bot/guest`. Cancelled games (cancel, expiry, not-started, show ended) are NOT counted; only `status = 'finished'`. The day is the calendar day in Europe/Warsaw of `finished_at` (DST-safe because the zone conversion is done by PostgreSQL). **Rust change:** `crates/gomoku-db/src/games/mod.rs::record_finished` currently lacks `AND g.origin <> 'show'`: add it (without it a finished show would be counted as `bot/bot` or `agent/bot`). A paper game is counted the same way (pair by kinds).

Backfill at introduction in Node (`finished` games still in `games`) is NOT needed in Rust (counter exists since F3; no data migration, plan: no data migration at all).

### 4.3 Read model (`gomoku_core::finished_stats`, new; port `finished-stats.ts` 1:1)
```
KNOWN_PAIRS (display order, each alphabetical):
  account-account, account-guest, account-agent, guest-guest, agent-guest, account-bot, bot-guest
PairCounter    { pair: "<a>-<b>", kinds: [a,b], total, today, last7Days }
FinishedGameStats { timeZone: "Europe/Warsaw", total, today, last7Days, pairs: [PairCounter] }
```
`build_finished_game_stats(rows)`: the 7 known pairs always present in that order (zeros when no row), then unknown pairs alphabetically by `pair` (`localeCompare`; use plain byte order, ASCII keys); `total/today/last7Days` are the sums over ALL pairs (unknown included). Row values may arrive as strings (numeric) -> convert. Unknown pairs are listed, never an error (the pairs `agent-agent`, `agent-bot`, `bot-bot` cannot occur once shows are excluded).
Aggregation SQL (read only, `now` bound as a parameter; windows computed in SQL in Warsaw time):
```sql
select c.kind_a, c.kind_b,
  sum(c.finished_count)::int as total,
  coalesce(sum(c.finished_count) filter (where c.day = t.today), 0)::int as today,
  coalesce(sum(c.finished_count) filter (where c.day between t.today - 6 and t.today), 0)::int as last7_days
from game_pair_counters c
cross join (select ($1::timestamptz at time zone 'Europe/Warsaw')::date as today) t
group by c.kind_a, c.kind_b
```
"Last 7 days" = today and the 6 days before (inclusive window of 7 days). The same reader backs the panel card and the (Node) `npm run stats:games` command; in Rust add `gomoku-db stats` subcommand (optional; Node prints the same structure) or skip and keep only the panel (owner decision, section 18).

### 5.2 Representation
| Field | bot vs bot | bot vs agent |
| --- | --- | --- |
| `games.origin` | `show` | `show` |
| `games.status` | `active` at creation, `started_at = now`, `black_seat` from `ColorDraw` at creation, `turn_started_at = now` (the clock runs at once) | `waiting` + one `invitations` row (code, `expires_at = now + 30 min`); colours drawn at the agent's `join` |

## 6. Show service (port of `ShowService`)

### 6.1 `create(admin_id, input)` order of checks (exact)
1. `config.show.enabled` else `503 SHOW_UNAVAILABLE` `data.reason = "disabled"`.
2. `bot-bot`: `!bot_vs_bot_enabled` -> `503 SHOW_UNAVAILABLE` `data.reason = "bot_vs_bot_disabled"`; `!bot_level2_enabled && levels contains 2` -> `503 BOT_UNAVAILABLE` `data.reason = "level2_not_allowed"` (+ `Retry-After: 60`; not logged).
3. Lazy settle then `current()`: if a show is open -> `409 SHOW_RUNNING` (BEFORE the rate-limit hit and the admission: a running show holds a bot slot itself, so admission would say `busy`, and each such refusal would spend the pool).
4. `rate_limiter.hit("show-create:{admin_id}", 10, 3_600_000)` -> `429 RATE_LIMITED` (+ `Retry-After`).
5. `admit_show(levels)`: `BOT_ENABLED` else `503 BOT_UNAVAILABLE` reason `disabled`; ONE memory reading (`resource_probe.read`) frozen in EVERY bot; `available_mb < BOT_MIN_AVAILABLE_MB` -> reason `memory` (log `bot.refused`); one `count_active_bot_games >= BOT_MAX_ACTIVE_GAMES` -> reason `busy` (log). A show counts as ONE game with the bot. Every refusal here: `503 BOT_UNAVAILABLE`, message `Bot jest teraz niedostępny. Spróbuj za chwilę albo zaproś osobę.`, header `Retry-After: 60`, and `data: {reason}` (reason ONLY on show routes, which only the admin reads). Strength per bot: `bot_strength_for(level, available_mb)` (F6).
6. Transaction (writes ONLY through the tx connection): `select pg_advisory_xact_lock(hashtext('show:create'))`; settle open shows again; if one is open -> `409 SHOW_RUNNING` (thrown AFTER commit so the lazy closing is kept); else insert (5.2). Two concurrent creations: exactly one wins, the other gets 409.
7. Log `security.show_created` (no fields). Response `201`.

`409 SHOW_RUNNING` body: message `Trwa już pokaz. Zakończ go albo wróć do niego.`, `data: {gameId, layout}` (layout of the OPEN show).

`current()` / settle-open: in one transaction, select open shows `g.origin='show' and g.status in ('waiting','active') order by created_at desc, id` with their bot count (`bots`); for each run `EXPIRE_WAITING_OF_GAME(now, id)` (waiting past `expires_at` -> `cancelled`) and the lazy timeout settlement; then re-select and return the newest still open as `{gameId, status, layout}`; `layout = bots == 2 ? "bot-bot" : "bot-agent"`.

### 6.2 `read(game_id, after)` (one transaction, this order)
1. `select status from games where id = $1 and origin = 'show'`: none -> `404 NOT_FOUND` "Nie znaleziono partii." (ANY non-show game, malformed id included, is the same 404; the admin cannot read other games through these routes).
2. `expire_waiting` for this game (now).
3. `START_SHOW_CLOCK`: `update games set turn_started_at = now where id=$1 and origin='show' and status='active' and turn_started_at is null and not exists (select 1 from game_players p where p.game_id = games.id and p.seen_at is null)` — the Rust `game_state`'s start-clock excludes the caller; the admin is nobody's seat so the show variant must NOT exclude a caller (a silent agent that never calls `get_state` still gets its clock and loses on time).
4. Lazy timeout settlement of this game (`settle_expired`).
5. Load game + players (order by seat); build the state (6.3). A cleanup deleting the game under the reader -> 404 (not a 500). `after` greater than `move_count` -> `400 VALIDATION` (`Nieprawidłowy parametr after.` is the shape error for non-digits/length > 5/ > 10201; the over-count message is the shared `AFTER_MESSAGE`; reuse the F3 handling of `GET /api/games/{id}?after=`).

### 6.3 `ShowState` (JSON of `GET /api/show/{id}` and the `end` response)
`spectator_view` (F4) MINUS `canChat` and `audience` and with players WITHOUT `seen`, PLUS: `layout`, `drive`, `invitation?`, `closedReason?`, `finishedAt?`. No `you`, no `rematch`, no `paper`, no tokens/e-mails/`seen`. Example (bot vs bot, mid-game; moves `[[7,7,1],...]` as in the F3 view):
```json
{"ok":true,"data":{
 "status":"active","variant":"classic","timeControlMs":600000,"moveCount":3,"blackSeat":2,"turnSeat":1,
 "moves":[...],"result":null,"board":"...as the F3 view...",
 "clock":{"remainingMs":[598200,597100],"running":1,"now":1790000000000},
 "players":[{"seat":1,"kind":"bot","displayName":"Bot · poziom 1","bot":{"level":1,"memoryMb":null,"tableMb":null}},
            {"seat":2,"kind":"bot","displayName":"Bot · poziom 2 · 16 MB","bot":{"level":2,"memoryMb":768,"tableMb":16}}],
 "layout":"bot-bot","drive":{"botOnTurn":true,"stalled":false}}}
```
(Field set of `board_view`/`clock` exactly as the Rust F3/F4 views already emit; `players[].agentName` present only for `kind:"agent"` as in `spectator_view`; `players[].bot` = `{level, memoryMb, tableMb}`.)
- `layout`: number of bot seats == 2 -> `bot-bot`, else `bot-agent`.
- `drive.botOnTurn`: `status == active` and some bot seat == `turnSeat`.
- `drive.stalled` (only computed when `botOnTurn`; else false): true iff the bot on turn has been on turn longer than a threshold, in SQL (`status='active'`, `turn_started_at` and `black_seat` set, bot seat on turn):
  `elapsed_ms(now - turn_started_at) > (pause_max_ms + 5000 + pending * (L2_ceiling + 500)) + (bot_level == 2 ? L2_ceiling : L1_ceiling)` where `pending` = computations queued or running at the process gate (incl. this show's own). Defaults, no queue: level 2 -> 2000+5000+3000 = **10 000 ms**; level 1 -> 2000+5000+250 = **7 250 ms** (Node test: params `[game, now, 7000, 3000, 250]`). Rust: expose `BotRuntime::pending()` (waiters + holder of the `Semaphore`; add a counter incremented before `acquire`, decremented after the search); `BOT_TERMINATE_WAIT_MS` has no Rust meaning (no thread kill: the engine cooperates every 1024 nodes), use 0 and keep the formula shape.
- `invitation` ONLY while `status == waiting`: `{code: "ABCD-EFGH" (formatted), url: "{origin}/invite/ABCD-EFGH", mcpUrl: "{origin}/api/mcp", expiresAt: ISO}`, `origin = APP_ORIGIN` else dev origin `http://localhost:3000` (same helpers as the F7 `invitation.mcpUrl`: `agent_mcp_url`, `invitation_url`). The code is a secret until the agent joins; once the agent has joined the key is ABSENT.
- `closedReason` (only `cancelled`): game has `started_at` -> `"ended"`; never started: the invitation's `consumed_at` set -> `"ended"` (the admin's end voids the code) else `"expired"`. (`expired` = the agent did not come in 30 min.)
- `finishedAt` ISO only for `finished` with `finished_at`.
- dates in the JSON are ISO strings (`iso_ms`).

### 6.4 `end(game_id)`
One transaction: `select status from games where id=$1 and origin='show' for update` (none -> 404); expire a waiting show; settle an expired clock FIRST (that result is kept); then
```sql
update games set status = 'cancelled',
  clock_ms_1 = case when status='active' and turn_started_at is not null and (case when move_count % 2 = 0 then black_seat else 3 - black_seat end) = 1
                    then greatest(0, clock_ms_1 - floor(extract(epoch from ($1::timestamptz - turn_started_at))*1000)::int) else clock_ms_1 end,
  clock_ms_2 = (same with seat 2),
  finished_at = case when started_at is not null then $1::timestamptz end
where id = $2 and origin='show' and status in ('waiting','active') returning id
```
(the clock that was running keeps the time it used; a show that had started keeps `finished_at`, so the agent's token stays valid one hour after, exactly as for any end, and the agent reads `cancelled` instead of an unknown token). When a row was updated: `update game_players set is_active = false where game_id=$1 and is_active` and `update invitations set consumed_at = now where game_id=$1 and consumed_at is null` (voids the code and lets `closedReason` tell "ended" from "expired"). Then return the state (6.3). If the show is `finished` (before or after the settle) -> `409 GAME_NOT_ACTIVE`, message `Ten pokaz już się zakończył.`, `data: {reason: "show_ended"}` (thrown AFTER the commit so the settlement stays). Repeating `end` on a `cancelled` show is harmless: `200`, nothing updated, same state. No result, no counter. Log `security.show_ended`.

### 6.5 `overview()` (`GET /api/show`) and `preflight(input)` (`POST /api/show/preflight`)
Checks (`ShowCheck {id, ok: bool|null, detail?: {..numbers}}`), in this order:
`show_enabled`; (bot-bot only) `bot_vs_bot_enabled`, and `level2_enabled` ONLY when `levels` contains 2; `bot_enabled`; `memory` (`ok = available_mb >= min_available_mb`, `detail {availableMb, minAvailableMb}`); `slot` (`ok = active_games < max_active_games`, `detail {activeGames, maxActiveGames}`); `no_show_running` (`ok = current == null`); `engine` (`ok: null` = not checked).
- `GET /api/show` -> `{enabled, botVsBotEnabled, level2Enabled, preflight: {ok, checks}, current: {gameId, status, layout}|null}`; preflight is for the default show (`bot-bot`, levels `[1,1]`), cheap, NO engine trial (`engine.ok = null`); `preflight.ok = every check.ok !== false` (null counts as fine).
- `POST /api/show/preflight` body = the create body; same checks, but `engine` is a real trial: one level-1 move on an EMPTY board through the production path (the compute gate + search, game id `preflight-<uuid>` so its failure count is forgotten after), `ok = the engine answered, no warning/error logged, ms <= BOT_L1_CEILING_MS (250)`, `detail {ms, limitMs, waitedMs}` (`ms` = the search's own time, `waitedMs` = wait for the gate). Response `200 {ok, checks}`.
Rust: add `BotRuntime::trial() -> EngineTrial{ok, ms, limit_ms, waited_ms}` using `SearchChooser` with the empty position, level 1, 600 000 ms clock; the engine "never fails a move" (falls back inline to level 1), so a trial that logged a fallback/engine error counts as failed.

## 7. Driving the show bot

### 7.1 Pure helpers (port into `gomoku-core::bot::show_pause`, vectors in F6 section 10)
`show_pause_ms(game_id, move_number, {min_ms,max_ms}) = min_ms + seed_of("show-pause:"+game_id, move_number) % (max_ms-min_ms+1)` (u32 modulo); `clip_show_pause(pause, clock_ms) = min(pause, max(0, floor(clock_ms/4)))`; `show_bot_limits(limits, l2_soft)`: ceiling = `min(limits[2].ceiling, 2*l2_soft)`, level 2 = `{soft: min(l2_soft, ceiling), ceiling}`, level 1 unchanged. `move_number` = the move the bot is about to make (`move_count + 1`).

### 7.2 `play_due_move` changes (Rust `gomoku-web/src/bot.rs::turn_inner`, `gomoku-db/src/games/bot.rs::bot_turn_due`)
- `bot_turn_due` must read ALL bot rows of the game (0-2): today it uses `fetch_optional` on `kind='bot'` and would pick the wrong bot (or error on two rows) in a bot vs bot show. Fetch all, pick the one whose `seat == seat_on_turn(move_count, black_seat)`; none on turn/none -> `Idle`. (A bug of the Node pre-show code too: stuck game forever.)
- Add to `BotTurn`/the read: `origin`, `clock_ms_at_turn_start` (the bot's stored clock, i.e. `clock_ms_{seat}`), `elapsed_ms = now_ms - turn_started_at_ms` (None before the clock starts), `variant`.
- Due rule: `status == active`, `variant == classic`, clock started (`turn_started_at` not null), `move_count < 225`; for `origin == 'show'` ADDITIONALLY `elapsed_ms >= clip_show_pause(show_pause_ms(game_id, move_count + 1, range), clock_ms_at_turn_start)` (the pause is counted from `turn_started_at`; the search starts only after it; no `sleep` in a request; `turn_started_at` is NOT changed so the pause is charged to the bot's clock). Ordinary games: no pause.
- Time limits: for `origin == 'show'` pass `show_bot_limits(config.bot.limits, show.bot_l2_soft_ms)` to the chooser instead of `config.bot.limits` (Rust `BotRuntime::choose` takes limits from its config: add an optional override on `BotTurn`).
- The move is written as the bot's seat through the normal `play_move` path (checks, clock charge, finish, `record_finished`, which skips shows). `LOST_RACE` set unchanged: `STALE_MOVE, GAME_FINISHED, NOT_YOUR_TURN, GAME_NOT_ACTIVE, GAME_NOT_STARTED`.
- Restart safety: the seed depends on game id and move number only (F6 R16), so a recomputation after a restart yields the same move; `in_flight` per game keeps two reads from computing twice.

### 7.3 Who calls it
1. `GET /api/show/{id}` (admin poll): after building the state, `if state.drive.botOnTurn { schedule_bot_turn(state, id) }` (the existing `tasks.spawn` runs it after the response). `end` does not schedule.
2. MCP `get_state` (F7), ONLY when the token's game has `origin = 'show'`: call `play_due_move(game_id)` at the start of EVERY round of the wait (before the readiness check) and, when `waitSeconds` is 0/absent, once before reading the state; `play_move` does NOT call it; chat and all other tools never drive. It never throws (outcome ignored). `FIND_BY_TOKEN` (`find_agent_seat`) must return `origin` (`seat.is_show`).
3. NOT triggered: ordinary games' MCP reads (bot never moves there), `resign`, finished games, `GET /api/games/{id}` of a show (the administrator is not a participant; players cannot read shows).

### 7.4 Client drive (`useShowDrive`; port into a `show-room.js`)
Loop reads `GET /api/show/{id}?after={known moves}` — the NEXT read is planned after the previous answer (never a fixed interval): 750 ms when the last state had `drive.botOnTurn`, 2000 ms otherwise; the first interval uses the botOnTurn of the page's initial state. A read is aborted after 8000 ms (counts as a failure). A hidden tab KEEPS polling (unlike the spectator room); coming back to the tab reads at once (`visibilitychange`). `check()` ("Sprawdź teraz" and clock expiry) = read now (coalesced: a request during an in-flight read sets `again`). The loop stops when the show is not `active`/`waiting` or the server answered 404 (`gone`). Status for the indicator:
`off` (not open) | `stalled{reason:hidden}` (tab hidden) | `stalled{reason:bot}` (`drive.stalled` from the server) | `stalled{reason:silent}` (3 failures in a row OR last success older than 5 s; ticks every 1 s) | `slowed{failures}` (1-2 failures) | `running`. Precedence in this order. Best-effort Screen Wake Lock (`navigator.wakeLock.request('screen')` while open and visible, re-requested on `visibilitychange`, released on close). When the running clock reaches 0 the view asks the server at once (only the server ends the game). Merging: `merge_state(known, new, after)` as in the game room (moves appended after `after`).

## 8. Bot vs agent flow (MCP, F7 seams)
1. Admin `POST /api/show {layout:"bot-agent", botLevel}` -> `waiting` game, bot in seat 1, invitation (30 min). The response carries `invitation {code,url,mcpUrl,expiresAt}` and `bots:[{seat:1,...}]`; the view `/show/{id}` shows the agent card.
2. The agent (any MCP client) calls `join {code|link, agentName?}` through the existing F7 path: `accept_invitation(JoinAs::Agent)`. Differences for shows: (a) `find_invitation` returns `creator_kind` (`bot`) and the join result `opponent.kind` becomes `"bot"` instead of the F7 hard-coded `"guest"|"account"` (`tools.rs::join_counted`: derive from `creator_kind`); (b) the creator has no user: the existing lock code already handles `creator_user_id = None`; (c) after seating, `update games set turn_started_at = $now where id = $1 and origin = 'show' and turn_started_at is null` (START_SHOW_CLOCK of the join: nobody else will "open" the game; both seats have `seen_at`); (d) colours drawn at the join (`black_seat` from `draw_black_seat`) — the bot may then move first: the first `get_state` of the agent (or the admin's poll) makes it play after its pause.
3. The agent's `get_state` drives the bot (7.3). Chat for the agent in a show is `unavailable` (bot opponent, F7). `join` description text already says `przeciwnikiem może być bot (opponent.kind = "bot")` and `administrator pokazu` — keep verbatim.
4. Browser path: `find_invitation` consumers for the BROWSER (`preview_invitation`, `accept_invitation` with `JoinAs::Account|Guest`, spectate-by-code, `/invite/{code}` page) must treat a show's code as unknown: `INVALID_INVITATION` (uniform with a wrong code, counts as a failed lookup in the existing lookup pool). Only `JoinAs::Agent` may consume a `show` invitation. Add `g.origin` to the `find_invitation` select and branch there.
5. A silent agent: the admin's reads start the clock (6.2 step 3); after 10 min `settle_expired` ends the game by `timeout` and the bot wins (a result, but still NOT counted).
6. Expiry: the show `waiting` past 30 min -> lazily `cancelled` (view: `closedReason: "expired"`); a waiting show does not hold a bot slot (`count_active_bot_games` counts `active` only); cleanup `waitingGames` removes it 1 h after the expiry.
7. Token validity for a show cancelled after it had started: the F7 predicate (`finished_at` set + 1 h) already covers it (`end` sets `finished_at`).

## 17. Where spec and code differ (code wins; ported as in the code)
1. Spec: `GET /api/show` returns `{enabled, preflight, current:{gameId,status,layout}}`. Code: also `botVsBotEnabled` and `level2Enabled`.
2. Spec: `403`/`500` possible for `requireAdmin` in routes; code: `requireAdminApi` throws `NotFoundError` -> 404 and runs BEFORE CSRF via `apiHandler`'s `gate` option.
3. Spec "API Contracts" check order: flags, pool, admission, transaction. Code: flags, then the check for a running show (`409`) BEFORE the pool and admission (review fix); the locked check inside the transaction still decides a race.
4. Spec: `409 SHOW_RUNNING` data `{gameId}`. Code: `{gameId, layout}`. Spec: create response `bots: [{seat, level, name}]`; code adds `tableMb` (`BotStrengthView`).
5. Spec: `closedReason` for `cancelled` by `started_at`. Code: also for a never-started show uses the invitation's `consumed_at` (admin's end voids the code).
6. Spec: `drive.stalled` = elapsed > `BOT_SHOW_PAUSE_MAX_MS + bot ceiling + 5000`. Code: also adds `pending_at_gate * (L2 ceiling + 500 ms)` (review of #305: a bot queued behind other games is not "stalled").
7. Spec: `START_SHOW_CLOCK_SQL` only in the admin read. Code: also executed after an agent's join (`AgentSeatService`), so the bot moves at the agent's first `get_state`.
8. Spec: the show counts in `GAME_COUNTERS_SQL` as P15 "excluded"; code: `where origin <> 'show'` on the WHOLE statement (status counts too) and `finishedByOrigin` has no `show` key.
9. Spec (panel): "Zakończone dziś / 7 dni" from `games.finished_at` with `date_trunc`; code: all pair data from `game_pair_counters` via `FinishedGameStatsService` (persistent, survives cleanup); panel "Partie w bazie teraz" and the two "w bazie" cards still count `games`.
10. Spec of the panel says "Brak migracji"; and for the account `finished` column "jak w historii": code counts all `finished` games of the account (including deleted opponents).
11. Spec: show `down()` refuses; Rust migrations are forward-only (no `down`).
12. Spec text mentions `END_SHOW_SQL` "bez wyniku"; code keeps `finished_at` for a started show (agent token window) — see 6.4.
13. Spec: P20 interpretation "toggle in the same view, not a separate route" confirmed by code (`?projektor=1` + localStorage default).
14. The `/show` link on the panel is static text `Pokaz partii botów (strona administratora)`; spec said it should exist without a home-page link: code matches.
15. Node `ShowPlayer.bot` has `{level, memoryMb, tableMb}` while `CreatedShow.bots` has `{level, tableMb}`: both ported as is.
16. PL catalog slip: `reason.silent.one` uses "sekundy" (see 12).
17. Node ran bot moves in `after()` of the route; the Rust equivalent is the existing `TaskTracker` spawn (`schedule_bot_turn`): the response is not delayed and tests can await it.
18. Node's drive worker thread/`BOT_TERMINATE_WAIT_MS` and `monitorEventLoopDelay` loop metrics (bench) have no Rust equivalent (async runtime, cooperative engine stop every 1024 nodes).
