## 0. How the variant differs from the classic game (one table)

| Aspect | Classic (F3) | Paper (F5) |
| --- | --- | --- |
| Board | 15x15, cell `y*15+x`, 0..224 | 101x101, absolute coordinates `x,y` in 0..100, no linear cell index on the wire |
| First stone | any cell | only the middle `(50,50)`, by black (the seat that moves first) |
| Legality | free cell on the board | free cell on the sheet AND within Chebyshev distance <= 3 of ANY stone (either player) |
| Goal | first five (or more) wins at once | five in a row never ends the game; every five scores; the game ends on time or by resignation |
| Scoring | none | `score(seat)` = sum over 4 directions and all maximal rows of that seat of `floor(len/5)`, recomputed from the stones |
| Clock | 10 min per player, fixed (`INITIAL_CLOCK_MS`) | per game: 1/2/3/5 min per player, default 3 min (`time_control_ms`) |
| Time runs out | the player on turn loses (`timeout`, winner = other) | player on turn NOT leading: game ends at the deadline, winner by points, equal = draw (`points`). Player on turn leading: the automat takes over (section 2.7) |
| End reasons | `five_in_row`, `draw`, `timeout`, `resignation` | `points` (winner or NULL = draw) and `resignation` only (resignation loses whatever the score) |
| Stored moves | `games.moves` bytea (1 byte/move), `games.move_count` | table `paper_moves` (x, y, seat, is_auto, played_at), count in `paper_game_states.move_count`; `games.move_count` stays 0, `games.moves` stays empty |
| Result JSON | `result.winLine` | `result.winLine = null`, `result.scores = [s1, s2]` (also for `resignation`); fives are in `paper.fives` |
| `moves` JSON | cells after `after` | `moves: []`; the stones are in `paper.moves` (objects) |
| Low-time threshold | 60 s | `min(60 s, tc/4)`: 15 s / 30 s / 45 s / 60 s for 1/2/3/5 min (classic 10 min -> 60 s) |
| Names of sides | black / white (czarne/białe) | marks: black = cross × (krzyżyk), white = nought ○ (kółko) |
| Review | step through the move log | no stepping ("review-paper-note"), players + result only |
| Bot | allowed | refused (`BOT_VARIANT_UNSUPPORTED`; out of scope here) |
| Shared unchanged | slot rule BR-13, invitation/accept, lobby pick/mark flow, cancel, rematch flow (settings copied), chat, public flag, spectators, pair counter, guest cookie rules, `READY_DEADLINE`, clock start when both saw the game, lazy settlement (no background job) |

## 2. Rules (pure functions; put them in a new `gomoku-core::paper` module, 100% covered)

Coordinates are `(x, y)`, `x` = column, `y` = row, both 0..100. Seats `1|2`. A stone is `{x, y, seat, auto}` (`auto` = placed by the automat). Colour is never stored: black = `games.black_seat`; black plays at even `move_count`; `seat_on_turn(move_count, black_seat)` is the classic function applied to the PAPER move count (auto stones count as moves).

### 2.1 `is_on_board(x, y)`
Both integers and `0 <= v < 101`. (Wire values are already 0..100, so `OFF_BOARD` is unreachable over HTTP; keep it in the pure function.)

### 2.2 `refusal(stones, x, y) -> Option<Refusal>`, in THIS order
1. not on board -> `OffBoard`
2. cell occupied (either seat) -> `CellOccupied`
3. `stones.is_empty()`: `(x,y) == (50,50)` ok, else `FirstMoveCenter`
4. exists a stone with `|dx| <= 3 && |dy| <= 3` (cells off the board skipped; NO wrapping at the edge) -> ok, else `MoveTooFar`
Index: `cell_key = y*101 + x` into a map `cell -> seat` (O(1) occupancy). Test vectors: `refusal([],50,50)=ok`; `refusal([],49,50)=FirstMoveCenter`; stone `(50,50)`: `(53,50)`,`(47,53)`,`(53,53)` ok; `(54,50)`,`(54,53)`,`(54,54)` `MoveTooFar`; stones `(50,50),(51,50,s2),(60,60,s2)`: `(63,63)` ok, `(64,64)` too far; stone `(100,10)` vs `(0,11)` -> `MoveTooFar` (no wrap).

### 2.3 `score_game(stones) -> { scores: [u32;2], fives: Vec<Five> }`
Depends ONLY on the set of stones (never on move order or any stored state).
```
own: map cell -> seat
for each stone s in stones (any order):
  for (dx,dy) in [(1,0),(0,1),(1,1),(1,-1)]:           # horizontal, vertical, diagonal down-right, diagonal up-right
    if has(s.x-dx, s.y-dy, s.seat): continue            # count a maximal row once, from its first stone
    len = 1; while has(s.x+dx*len, s.y+dy*len, s.seat): len += 1
    n = len / 5 (integer division); scores[s.seat] += n
    for k in 0..n: start = 5*k
       fives.push({seat, from:(x+dx*start, y+dy*start), to:(x+dx*(start+4), y+dy*(start+4))})
sort fives by (seat, from.y, from.x, to.x)  # stable; see tie rule below
has(x,y,seat) = on_board(x,y) && own[cell(x,y)] == seat
```
- A row is a maximal run of the SAME seat's stones; an opponent stone or an empty cell breaks it; nothing wraps around an edge.
- Row of 6..9 = 1 point (the whole row is "used" in that direction); 10..14 = 2; 15 = 3.
- A stone belongs to rows of all four directions (crossing allowed): 9 stones in a cross -> 2; 13 stones through one stone in 3 directions -> 3; 17 in 4 directions -> 4.
- `fives` cuts a scoring row into consecutive fives from the end with the smaller coordinate (smaller x; for ↗ the end with smaller x, which has the LARGER y). The leftover stones (len mod 5) are not in any five. `from`/`to` are the first and last stone of the five.
- **Tie rule (determinism, Rust must match Node byte for byte):** Node sorts by `(seat, from.y, from.x, to.x)` with a STABLE sort over insertion order (stones iterated in move order, directions in the order above). Equal keys occur only for different directions starting at the same stone with the same `to.x` (horizontal vs ↘ vs ↗ all have `to.x = from.x+4`). Rust: sort by `(seat, from.y, from.x, to.x, direction_index)` with `direction_index` h=0, v=1, d↘=2, a↗=3 (this reproduces Node's order independently of the stone iteration order).
- Complexity O(stones x 4 x row length); full recomputation on each move/poll/settle is fine.

### 2.4 `pick_auto_move(stones, around, random) -> Option<(x,y)>`
The cell the automat plays for a player (BR-50): Chebyshev rings `r = 1, 2, ..., 100` around `around` (the opponent's last stone). For each ring collect, in fixed order (rows `y` ascending, then columns `x` ascending), the cells at distance exactly `r` that are on the board and have `refusal(...) == None`. The first non-empty ring wins; pick index `min(floor(random()*len), len-1)`. `None` only when the sheet is full. Rings 1..3 around any stone are always legal (BR-47), so in practice the first ring with a free cell is used. Rust: inject `random_int(len) -> usize` (like `draw_black_seat`); parity vectors use `random() = 0` -> index 0 and `0.9999` -> last, and `random = 1` is clamped to last.
Vectors: stone `(50,50)` seat 1, `around=(50,50)`: random 0 -> `(49,49)`, 0.9999 -> `(51,51)`. Ring 1 fully occupied (3x3 block) -> a ring-2 cell. Stone at `(0,0)` -> only on-board cells. Full sheet -> `None`. Stones: five of seat 1 at `(40..44,50)`, seat 2 at `(41,51),(42,51)`, `around=(42,51)`: random 0 -> `(43,51)` (row y=50 and `(41,51)` are taken), random 0.9999 -> `(43,52)`.
`around` choice (in `resolve`): the LAST stone (by move order) whose seat is not the automat's seat, falling back to the last stone overall when the opponent has none.

### 2.5 Clock charge of a move (reuses `clock::spend`)
Normal phase (`auto_seat IS NULL`): the mover's remaining = `stored - max(0, now - turn_started_at)` (clamped 0..time_control), `turn_started_at = now` (opponent's clock starts), the opponent's value unchanged. Automat phase: a move of the human opponent charges NOTHING and does not touch `turn_started_at` (their clock runs without a break from the take-over moment `T`, section 2.7). `stored` clamps to the game's `time_control_ms`, NOT to 600000: set `ClockState.time_control_ms = Some(game.time_control_ms)` (the field exists; today `GameRow::clock_state` passes `None`).

### 2.6 Which clock runs / which seat is "on turn"
- `turn_seat` (JSON `turnSeat`) = `seat_on_turn(paper_move_count, black_seat)` while `active`, including the automat's turns (`turnSeat == autoSeat` means "the automat is to move").
- The clock seat (the seat whose clock runs and whose deadline matters) = `other(auto_seat)` in the automat phase, else `turn_seat`. `clock.running` = that seat iff `turn_started_at IS NOT NULL`, else `null`. `clock_view` is called with the CLOCK seat as `turn_seat`.
- In the automat phase `clock_ms[auto_seat] = 0` and `turn_started_at = T` (the take-over instant) for the whole phase.

### 2.7 `resolve_paper_clock(state, now_ms, random) -> { auto_moves, finish, state }` (the lazy timeline, BR-50)
Input `PaperClockState { stones, clock_ms[2], turn_seat (= CLOCK seat), turn_started_at_ms (floored to ms), auto_seat, pending_auto_at_ms }`. Output: automat stones to append (each stamped with the moment it happened), an optional finish `{at_ms, winner_seat|None}` and the new state. Pure; `now_ms` and `random` injected.
```
if auto_seat is None:                                   # normal phase
    deadline = turn_started_at + clock_ms[turn_seat]
    if now < deadline: return (no moves, no finish, state unchanged)
    scores = score_game(stones)
    leads = scores[turn_seat] > scores[other(turn_seat)]
    if !leads  or  !play_auto(turn_seat, deadline):      # play_auto false = sheet full
        return finish {at: deadline, winner: winner_of(stones)}   # higher score wins, equal -> None (draw)
    # take-over: the automat has played at `deadline`
    state = { stones, clock_ms[turn_seat] = 0, turn_seat = other(turn_seat),
              turn_started_at = deadline, auto_seat = (old turn_seat), pending_auto_at = None }
# automat phase (also entered above in the same call)
player = other(auto_seat); player_deadline = turn_started_at + clock_ms[player]
pending = state.pending_auto_at
if pending is Some and pending < player_deadline and now >= pending:
    play_auto(auto_seat, pending); pending = None
if now >= player_deadline:
    return finish {at: player_deadline, winner: winner_of(stones)}
return (moves, no finish, state with new stones/pending)
play_auto(seat, at) = pick_auto_move(stones, around(stones, seat), random) -> push stone{seat, auto:true}, record move at `at`
```
Notes: every automat stone and the end carry the moment they happened (never `now`), so a late poll reproduces the continuous timeline; the first automat stone is at the take-over deadline `T`; later stones at `pending` (= opponent's move time + 2000). A pending stone due AFTER the opponent's deadline is never played. At most ONE pending stone exists (the automat plays right after the human). The automat plays only the leader's seat; if the human later catches up (even overtakes) the automat still plays for the original seat and the winner is decided by points at the human's deadline. Finish `winner_of`: `scores[0] == scores[1]` -> `None`, else higher.
`auto_due_at(at_ms) = at_ms + 2000` (set by the move service, section 5.4).
Vectors (T0 = 1_000_000; seat 1 black, five at `(40..44,50)`, seat 2 stones `(41,51),(42,51)`, `clock_ms=[30000,40000]`, `turn_seat=1`, `turn_started=T0`, random=0):
1. now = T0+29_999 -> nothing.
2. same but `turn_seat=2` (trailing on turn), now = T0+100_000 -> finish `{at: T0+40_000, winner: 1}`, no stones.
3. equal scores (one stone each), turn seat 1, now = T0+30_000 -> finish `{at: T0+30_000, winner: None}`.
4. leader on turn, now = T0+30_000 -> one auto stone `(43,51)` seat 1 at `T0+30_000`; state `{auto_seat: 1, turn_seat: 2, turn_started: T0+30_000, clock_ms: [0, 40000], pending: None}`; stones +1.
5. sheet full (rows y<=70 seat 1, others seat 2), now = T0+31_000 -> finish `{at: T0+30_000, winner: 1}` (automat has no cell), no stones.
6. automat phase with `pending = T0+40_000`: now = pending-1 -> nothing (pending kept); now = pending+5_000 -> auto stone at `pending`, `pending = None`, `turn_started` unchanged.
7. automat phase, now >= `T0+30_000+40_000`+999 -> finish `{at: T0+70_000, winner: 1}`. Pending stone with `pending = deadline+1` and now = deadline+5_000 -> no stone, same finish.
8. human catches up (two extra fives of seat 2) -> finish `{at: T0+70_000, winner: 2}`.
9. Idempotence: `resolve(start, T0+500_000)` has the same `finish` as `resolve(start, T0+30_000)` then `resolve(result.state, T0+500_000)` (= `{at: T0+70_000, winner: 1}`).
10. `auto_due_at(T0) = T0+2000`.

### 2.8 `paper_view(snapshot, after) -> PaperView`
```
snapshot = { move_count, auto_seat, pending_auto_at_ms, moves: [{n,x,y,seat,auto,at_ms}] }
view = { moveCount, moves: moves with n > after as {n,x,y,seat,auto,at: iso_ms(at_ms)},
         scores, fives (from score_game over ALL moves), autoSeat, autoMoveAt: iso_ms(pending) | null }
```
`at` of a human move = the instant the move was accepted; of an automat stone = the moment it was due (`T` or `opponent move + 2000`), not the detection time.

## 3. State model and lifecycle differences

A paper game is a normal `games` row (header: origin, status, black_seat, clocks, rematch, public flag, ...) plus ONE `paper_game_states` row (1:1, created in the same transaction as the game in EVERY creation path) plus N `paper_moves` rows. Everything about participants, invitations, chat, spectators, lobby slot, pair counter is shared and unchanged.
Lifecycle (status machine of F3 section 3 is unchanged). Differences only in `active`:
- clock start, cancel-not-opened (15 min), join, lobby pick, rematch accept: identical (clock budget is the game's `time_control_ms`: `clock_ms_1 = clock_ms_2 = time_control_ms` on insert).
- `active -> finished` happens by: **resign** (`resignation`), **lazy end by points** (`points`) found by any touch (`settle`). There is no five-in-row/draw/timeout finish. `finished_at` for `points` = the deadline (moment time ran out), not the detection time; `winner_seat` NULL for equal points.
- Slots are released in the same transaction as the finish (as in F3); the pair counter is written (`record_finished`).
- A game where nobody moves: black's clock runs from the start (when both saw the game); at the deadline scores are 0:0 -> finish as a draw by points (`winner_seat NULL`, `end_reason 'points'`), clock of black 0.

```sql
  game_id     uuid        NOT NULL REFERENCES games (id) ON DELETE CASCADE,
  move_number integer     NOT NULL,                     -- 1.. per game, includes automat stones
  x           smallint    NOT NULL,
  y           smallint    NOT NULL,
  seat        smallint    NOT NULL,
  is_auto     boolean     NOT NULL DEFAULT false,
  played_at   timestamptz NOT NULL,                     -- human: when accepted; automat: when due (see 2.8)
  PRIMARY KEY (game_id, move_number),
  CONSTRAINT paper_moves_game_id_x_y_unique UNIQUE (game_id, x, y),      -- a field holds at most one stone
  CONSTRAINT paper_moves_move_number_check CHECK (move_number >= 1),
  CONSTRAINT paper_moves_coordinates_check CHECK (x BETWEEN 0 AND 100 AND y BETWEEN 0 AND 100),
  CONSTRAINT paper_moves_seat_check CHECK (seat IN (1, 2)));
```
Notes:
- `auto_seat = S` => `clock_ms_S = 0` and `turn_started_at = T` cannot be a CHECK; the settler and an integration test guarantee it. `score_n` is a cache (history reads it); the API serves scores recomputed from `paper_moves`.
- No `bit(225)`/stones columns exist in the Rust schema, so the Node `games_stone_count_check`-style constraints are not involved; `games_moves_length_check` (`octet_length(moves)=move_count`) keeps holding for paper (0 = 0).
- Cascade: deleting a game (cleanup, account deletion of waiting games) deletes its paper rows; nothing else to do.
- `game_pair_counters` unchanged (no variant dimension). Pair counter counts a `points` finish like any other.
- Unique violations: a second stone in a cell or a duplicate `move_number` can only happen if the row lock is bypassed; map `paper_moves_pkey` / `paper_moves_game_id_x_y_unique` violations to `STALE_MOVE` (409) instead of a 500.
- Node's `down` refused when paper games exist; Rust migrations are forward-only (state the decision in the PR; if a down script is wanted, copy that guard).
- Cleanup deadline SQL (shared by the `guestOnlyActiveGames` rule AND the `chatMessages` rule of F4): see 5.13.

### 5.3 `game_state` (the poll) — order of operations (changes to F3 4.4)
1. `move_count` for the `after` check = `COALESCE(paper_game_states.move_count, games.move_count)` (LEFT JOIN `paper_game_states`); `after > move_count` -> `BadAfter` (400) before any write.
2. EXPIRE / CANCEL_NOT_STARTED / START_CLOCK exactly as F3.
3. `settle_expired(game)`: variant dispatch. Classic: unchanged. Paper: `paper_is_due(game_id, now)` WITHOUT a lock; only if due: `SELECT id FROM games WHERE id = $1 FOR UPDATE`, then `settle_paper`.
4. MARK_SEEN last; then `snapshot()` (loads the paper snapshot).
`paper_is_due`: row `status='active' AND black_seat IS NOT NULL AND turn_started_at IS NOT NULL`; `deadline = turn_started_ms + clock_ms[clock_seat]`; `pending = pending_auto_at_ms` (infinity when NULL); due iff `now_ms >= min(deadline, pending)`. (A normal poll stays a plain read.)

### 5.4 `settle_paper(conn, game_id, now, random) -> { finished, changed }` (row already locked)
```
read game header + paper state; if not (active && black_seat && turn_started_at) -> none
state = PaperClockState{ stones from paper_moves (ordered), clock_ms[2], turn_seat = clock_seat (2.6),
                         turn_started_ms (floored), auto_seat, pending_auto_ms }
resolved = resolve_paper_clock(state, now_ms, random)
if resolved.auto_moves.is_empty() && resolved.finish.is_none(): return none
for (i, m) in auto_moves: INSERT paper_moves (game_id, move_count+1+i, x, y, m.seat, is_auto=true, played_at = m.at_ms)
scores = score_game(resolved.state.stones); move_count' = move_count + auto_moves.len()
UPDATE paper_game_states SET move_count = move_count', score_1, score_2, auto_seat = resolved.state.auto_seat,
       pending_auto_at = NULL, last_move_at = last auto stone's at (or unchanged) WHERE game_id = $1
if the automat took over in this call (state.auto_seat was None, resolved.state.auto_seat is Some):
   UPDATE games SET clock_ms_<auto seat> = 0, turn_started_at = resolved.state.turn_started_at WHERE id = $1 AND status = 'active'
if resolved.finish is None: return {finished: false, changed: true}
UPDATE games SET status='finished', winner_seat = finish.winner|NULL, end_reason='points', finished_at = finish.at,
       clock_ms_<resolved.state.turn_seat> = 0 WHERE id = $1 AND status = 'active' RETURNING id
   -- the zeroed clock is the CLOCK seat's (the one that ran out): the player in the automat phase, the seat on turn otherwise
if no row: {finished: false, changed: true}
record_finished(game); release_slots(game); return {finished: true, changed: true}
```
`pending_auto_at` is always rewritten to NULL here (a due stone was just played or a take-over has none yet).

### 5.5 `play_move` for paper (`GameMoveService.play` branch)
In `lock_for_play` read `variant` too. After the locked read and `now`:
- classic: unchanged (but now bounds are validated here, section 6.3).
- paper (inside the same transaction, refusals RETURNED, not thrown, so a settlement written on the way is committed; throw after commit; "settled" => commit then `GameFinished`):
  1. **Retry**: `SELECT x, y, seat FROM paper_moves WHERE game_id = $1 AND move_number = $2` (the number the client sends); same seat and same `x,y` -> return the state with `after = move_number - 1`, write nothing (200).
  2. `settle_paper`; `finished` -> commit, `409 GAME_FINISHED`.
  3. re-read status: `finished` -> `GAME_FINISHED`; not `active` or no black seat -> `GAME_NOT_ACTIVE` (`reason game_not_active`); `turn_started_at IS NULL` -> `GAME_NOT_STARTED`.
  4. load paper snapshot; `on_turn = seat_on_turn(snapshot.move_count, black)`. If `on_turn != seat` **or** `snapshot.auto_seat == Some(seat)`: `NOT_YOUR_TURN` with `data.reason = "auto_turn"` and message "Automat stawia kamień." when `on_turn == auto_seat` (it is the automat's turn), else `reason "opponent_turn"`, "Teraz ruch przeciwnika.". (The seat the automat plays for never moves by hand, even if the model says it is on turn.)
  5. `move_number != snapshot.move_count + 1` -> `STALE_MOVE`.
  6. `refusal(stones, x, y)`: `CellOccupied` -> `409 CELL_OCCUPIED`; `OffBoard` -> `400 VALIDATION` "Pole jest poza planszą."; `FirstMoveCenter` -> `400 FIRST_MOVE_CENTER` "Pierwszy kamień trafia na środek planszy."; `MoveTooFar` -> `400 MOVE_TOO_FAR` "Kamień może stać najwyżej 3 pola od innego.". **Turn check before stale check before the board checks.**
  7. `scores = score_game(stones + new)`; `pending = if auto_seat.is_some() { now + 2000 ms } else { NULL }`.
  8. `UPDATE paper_game_states SET move_count = move_count + 1, score_1, score_2, pending_auto_at = pending, last_move_at = now WHERE game_id = $1 AND move_count = $snapshot_move_count RETURNING game_id` (0 rows -> `STALE_MOVE`); `INSERT paper_moves (..., is_auto = false, played_at = now)`.
  9. Clock: only when `auto_seat IS NULL`: `spend(clock_state(turn_seat = seat), seat, now)`; `UPDATE games SET clock_ms_1, clock_ms_2, turn_started_at = now WHERE id = $1 AND status = 'active'`. In the automat phase no clock write (their clock runs from `T`).
  10. return `stateOf(after = move_number - 1)`.
- A paper move never finishes the game (no five-in-row end), so no `record_finished`/`release_slots` here.
The "retry" detection precedes the settle, so a retried winning-nothing move after the game ended on time still answers 200 (same as classic).

### 5.6 `resign` for paper
Identical to F3 4.7 with `settle_game` dispatching to `settle_paper`: (1) repeat by the same resigner -> 200; (2) settlement finished the game by points -> commit then `409 GAME_FINISHED` (the loss on time/points wins over the resignation; materialised automat stones without a finish are kept); (3) `resolve_resignation`; (4) `UPDATE ... end_reason='resignation', winner = other seat, finished_at = now`; `record_finished`; `release_slots`. ### 7.4 PaperBoard (new component; port of `paper-board.tsx` + `paper-board-view.ts` to JS; tokens already in `assets/game-tokens.css`)

## 10. Edge cases and tests worth porting (all verified in Node tests/code)

1. Create: classic with `timeControlMs` -> 400 (`TIME_CONTROL_CLASSIC`); `{variant:"paper", timeControlMs:90000}` -> 400 (`invalid_union`); `{variant:"renju"}` -> 400 (`invalid_value`); `{variant:"paper"}` -> 180000; `{}`/no body -> classic 600000 and NO `paper_game_states` row and no `paper` key in the view; `{variant:"paper", timeControlMs:120000}` stores clocks 120000/120000 and an empty sheet row (`move_count 0, score_1 0, score_2 0, auto_seat NULL`); view of a waiting paper game: `paper = {moveCount:0, moves:[], scores:[0,0], fives:[], autoSeat:null, autoMoveAt:null}`, `clock.remainingMs [120000,120000]`, `running null`.
2. Rules over HTTP: first stone elsewhere -> `400 FIRST_MOVE_CENTER`; white moving first -> `409 NOT_YOUR_TURN`; `(50,50)` ok -> `paper.moves = [{n:1,x:50,y:50,seat:black,auto:false}]`; same move again (same number) -> 200, `moveCount` 1; black again -> `NOT_YOUR_TURN`; white on `(50,50)` -> `409 CELL_OCCUPIED`; `(55,50)` -> `400 MOVE_TOO_FAR`; `(51,50)` with number 3 -> `409 STALE_MOVE`; `x=101` -> `400` (route schema); after a 400/409 nothing changed (`move_count` still 1); `(53,50)` ok -> `moveCount` 2 and `turnSeat = black`; `paper_moves` rows hold both stones; `games.move_count` stays 0 and `moves` empty.
3. Scoring flow: black row of 5 (`(50..54, ROW_Y)`) interleaved with white stones elsewhere -> status still `active`, `paper.scores` = `[1,0]` or `[0,1]` by `blackSeat`, `fives.len()==1`, `paper_game_states` = `score_1/2`, `move_count 9`. The mover's clock is charged (first move 5 s after the clock started -> stored remaining in `(54000, 55500]` for a 60 s game).
4. End by time: trailing player on turn runs out -> any read finishes the game: `finished`, `reason points`, winner = the leader, `end_reason 'points'`, slots released; a later move -> `409 GAME_FINISHED`, nothing written. Equal scores -> `winnerSeat null`, `end_reason points`, `winner_seat NULL`.
5. Automat: leader (black on turn) runs out at `T` -> one read creates the automat stone (`auto true`, seat = leader, `at = T`, within distance 1 of the opponent's last stone), `autoSeat = leader`, `clock_ms[leader] = 0`, `clock.running = opponent`; opponent's own move at that time answers 200; the leader's move attempt while the OPPONENT is on turn -> `NOT_YOUR_TURN` "Teraz ruch przeciwnika."; after the opponent moves `autoMoveAt` is set (= move time + 2 s) and the leader's attempt now -> `NOT_YOUR_TURN` "Automat stawia kamień."; after >= 2.5 s a read shows `moveCount + 1`, an automat stone adjacent (ring 1) to the opponent's last stone, `autoMoveAt null`; when the opponent's clock expires: `finished`, `reason points`, winner by points, `clock_ms[opponent] = 0`, slots released. Polling a game 5 minutes late gives the same moves/finish as continuous polling.
6. Resign: the LEADER resigning loses (`winnerSeat = other`, `reason resignation`, `result.scores` present); resign after the time has run out on a points-ended game -> `409 GAME_FINISHED` with the points result kept; repeat by the resigner -> 200.

## 11. Gaps, differences spec vs code, suspected bugs and decisions the Rust side must make

### 11.1 Spec vs code (follow the CODE)
1. The spec's timeline table says the human opponent's move is refused with `409 AUTO_MOVE_PENDING`; the code answers `409 NOT_YOUR_TURN` with `data.reason = "auto_turn"` and the message "Automat stawia kamień." (an ordinary "Teraz ruch przeciwnika." when the OPPONENT is on turn). The spec also says the reason is `opponent_turn` for this case; it is `auto_turn`.
2. The spec says `points` for `resignation` results "may carry `result.scores`": the code ALWAYS sets `scores` on a finished paper result (both reasons).
3. The spec says the schema `after` bound for classic stays 225: Node's route actually uses the paper bound (10201) for both variants (F3 gap 10.1-7); the service enforces `after <= moveCount`.
4. The spec mentions "`LOW_TIME` for paper = min(60 s, 25% of the game)" as a reversible agent proposal; it is implemented (`low_time_ms`).
5. The spec's MCP slice (`boardOrigin`, 101-row avoidance) is the F7 seam; HTTP carries no `board` for paper.
6. Review: the spec's "review step-through of paper" is NOT implemented: paper reviews show a note (`review.paperTitle/Body`).

### 11.2 Suspected bugs / oddities in Node (decide consciously; I changed nothing)
1. `paper_game_states.last_move_at` is write-only (never read): drop it or keep for parity.
2. `OFF_BOARD` is unreachable over HTTP (wire bound = board bound) but still has a message ("Pole jest poza planszą.") and a `VALIDATION` code without a field; keep the pure function and the mapping.
3. `settle` writes `pending_auto_at = NULL` whenever anything was written, which is correct only because a due stone was just played or a take-over has none; keep this invariant (do not add a second pending slot).
4. Equal key tie in the `fives` sort is resolved by JS's stable sort + iteration order (see 2.3): Rust must use an explicit direction index.
5. A paper game that nobody plays ends as a 0:0 draw (`points`, winner NULL) after the first player's budget; the history shows it as a draw; the pair counter counts it. Product-wise questionable but it is the shipped behaviour.
6. Guest rematch: F3 limits apply (55 min window); the clock budget copied from the old game.
7. The retry detection of a paper move runs BEFORE the settlement and the status checks (like classic): a retried move after the game ended on time still answers 200 with the finished state.
8. `timeControlMs` on `PUT /api/lobby/seeking` while a live status exists is silently ignored (the old status is returned).
9. Pair counters have no variant dimension; the admin overview (F8) cannot split classic/paper.
10. The history `scores` come from the cache columns (`score_1/2`), while the API serves recomputed scores; they agree because every stone-writing path rewrites the cache in the same transaction. A Rust change that adds a new stone-writing path MUST update the cache.

### 11.3 Decisions for the Rust side
1. **RNG injection** into `Database` (5, header) vs passing it per call: recommended inside `Database` with a test constructor.
2. **PaperBoard logic in JS only** (agent-browser tests with the vectors of 7.4) vs a mirrored pure module in `gomoku-core` (100% line/function coverage rule applies to core, not to JS): recommended JS-only with agent-browser coverage; the DOM contract in 7.4 is what the tests pin.
3. Whether to load only `move_number > after` rows for the view: scoring needs every stone, so keep loading all (<= ~600 rows).
4. Forward-only migration (no `down`), see 4.
5. Where to put the classic move-bound validation (service, after the participant lookup): required to keep the classic contract identical (F3 gap 10.1-8 becomes moot).
6. Public paper games: allowed (spectators see the paper view); nothing blocks it.
