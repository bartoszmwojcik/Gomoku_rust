```sql
  user_id      uuid null references users(id) on delete cascade,     -- an account spectator
  nickname     varchar(24) null,                                      -- a visitor's optional nickname (1..24)
  token_hash   char(64) null,                                         -- sha256 hex of the spectator cookie token (visitor)

  constraint game_spectators_nickname_check check (nickname is null or (token_hash is not null and char_length(nickname) between 1 and 24)),  -- only a visitor picks a nickname

);
create index game_spectators_expires_at_index on game_spectators (expires_at);                 -- cleanup
create index game_spectators_game_id_last_seen_at_index on game_spectators (game_id, last_seen_at);  -- presence count
create index game_spectators_user_id_index on game_spectators (user_id);                        -- cascade of delete from users

create table chat_messages (
  id           uuid primary key default gen_random_uuid(),
  game_id      uuid not null references games(id) on delete cascade,
  seq          integer not null,                                       -- message number in the game 1,2,3..; the cursor `after_id`
  sender_id    uuid null references game_players(id) on delete cascade,        -- a player's message
  spectator_id uuid null references game_spectators(id) on delete cascade,     -- a spectator's message
  author_name  varchar(24) null,                                       -- spectator's nickname / account display_name AT SEND TIME (never an e-mail)
  client_id    uuid not null,                                          -- id of one send attempt (idempotence)
  body         varchar(1000) not null,                                 -- stored already NFKC-normalized and trimmed
  created_at   timestamptz not null default now(),                     -- inserted with clock_timestamp()
  constraint chat_messages_game_id_seq_unique unique (game_id, seq),
  constraint chat_messages_sender_id_client_id_unique unique (sender_id, client_id),
  constraint chat_messages_spectator_id_client_id_unique unique (spectator_id, client_id),
  constraint chat_messages_seq_check check (seq >= 1),
  constraint chat_messages_author_check check (
    (sender_id is not null and spectator_id is null and author_name is null) or
    (sender_id is null and spectator_id is not null and author_name is not null)),
  constraint chat_messages_body_length_check check (char_length(body) between 1 and 1000)

-- The uniques also cover the FK columns (game_id, sender_id, spectator_id): no extra index.
```

Notes:
- The message holds NO account id, e-mail, IP, user agent. The API returns the seat (`seat`) for a player and `spectatorName` for a spectator, never an id.
- `seq` is allocated as `coalesce(max(seq),0)+1` in the INSERT, under the per-game advisory lock (4.1), so it grows in commit order and the cursor never skips. Gaps appear only when messages are deleted (kill-switch, cleanup).
- Deleting the account: `game_spectators.user_id on delete cascade` -> the spectator's messages go (FK `spectator_id` cascade). A player's messages are deleted explicitly (section 7.2). Deleting a game cascades to messages and spectators.
- Down-migration note of the old code: messages are temporary by design (BR-34), losing them on `down` is accepted.

## 2. Game chat (E07-S01, S02, S03; spectator parts in section 4)

### 2.1 Product rules

1. Participants: the two players (account or guest). Each player has `game_players.chat_enabled` (default true), set only by that player (2.5). A rematch is a NEW game: new `game_players` rows, switch `true`, empty chat (R14).
2. A message is ONE line of plain text, 1..200 code points after NFKC + trim of ASCII spaces; no control or invisible characters; no web addresses (2.2). It is stored in its normalized form. Text is always rendered as a text node (never HTML, never a link).
3. Sender interval: at most 1 message / 2000 ms per sender (DB clock). Game cap: 500 messages (all senders). Not via `rate_limit_buckets`.
4. Chat availability by game state (`deriveChatState`, section 2.3): `waiting` and `cancelled` = `unavailable`; `active` = open; `finished` = open for 1 h after `finished_at` (DB `now()`), then `closed` (no content in the answer even if cleanup has not removed it yet). Applies to ALL participant kinds, accounts too.
5. A game in which a seat belongs to a DELETED account (`kind = 'account'` and `user_id IS NULL`, any seat) has chat state `unavailable` (read returns no content, send `409 CHAT_UNAVAILABLE`): the conversation was deleted with the account and `seq` would restart under a client's cursor.
6. Disabling is per player: the one who turned it off neither sees the conversation nor writes (`disabled_by_you`, empty list); the other player keeps seeing the history but cannot write (`disabled_by_opponent`, send -> `409 CHAT_DISABLED`). The history returns for the one who turns it on again (the other side could not write meanwhile, so nothing is lost). Exception for PUBLIC games: see 2.3 (`isPublic`).
7. No moderation, no reporting, no persistent mute (N-11). No logs of text, `clientId` or text-bearing errors anywhere (error messages never echo input; do not log request bodies).

### 2.2 `normalizeChatMessage(raw, {maxLength})` (pure, `core/chat/message.ts`; port exactly)

Returns `{ ok: true, text }` or `{ ok: false, reason }`, `reason` one of: `not_text`, `empty`, `too_long`, `control_char`, `invisible_char`, `combining_run`, `url`.
Order:
1. `raw` is not a string -> `not_text`.
2. `raw.length > 1000` (UTF-16 units, BEFORE normalization) -> `too_long`.
3. `s = NFKC(raw)`, iterate code points (index i):
   - category `Cc`, `Cs` (lone surrogates cannot occur in Rust strings; keep for parity), `Zl`, `Zp` -> `control_char` (a newline is `Cc`, so multi-line text is `control_char`);
   - a ZWJ U+200D whose previous AND next code points are both `Extended_Pictographic` (single code point) is allowed (emoji sequences) and skipped; any other ZWJ falls to the next rule;
   - `invisible_char` for: categories `Cf`, `Co`, `Cn`; code points U+034F, U+115F, U+1160, U+3164, U+FFA0, U+2800; variation selectors U+FE00..U+FE0E and U+E0100..U+E01EF (U+FE0F is allowed); any `Zs` other than ASCII space U+0020 (NFKC maps most spaces to U+0020 first);
   - combining run: counter of consecutive `\p{M}` code points (reset by any non-mark); `> 4` -> `combining_run`. (Order of the above inside one code point: control, ZWJ exception, invisible, then the combining counter.)
4. `text = join(code points)` with ASCII spaces trimmed at both ends (`^ +| +$`, ONLY U+0020). Empty -> `empty`.
5. `codepoint_count(text) > maxLength` -> `too_long`.
6. URL heuristic on `text` after replacing U+3002 (ideographic full stop) with `.` (U+FF0E is already `.` after NFKC): refuse (`url`) if ANY of:
   - scheme with `://`: `[a-z][a-z0-9+.-]*://` (case-insensitive);
   - dangerous scheme directly followed by a non-space: `(^|[^\p{L}\p{N}])(mailto|javascript|data|file|vbscript):(?=\S)` (case-insensitive) - "Jaka data: dziś" passes;
   - `(^|[^\p{L}\p{N}])www\.` (case-insensitive);
   - IPv4: `(^|[^\d.])(\d{1,3}\.){3}\d{1,3}(?!\d)`;
   - domain: `[\p{L}\p{N}][\p{L}\p{N}-]*\.(TLD)(?![\p{L}\p{N}])` where TLD is one of `com net org info biz xyz io gg ly cc tv ws ai app dev link site online shop club pl eu de uk ru cz sk fr es nl`, written ALL lower case or ALL upper case (so "Cześć.Co tam" and "Dobra.Gramy" pass, "ok.com"/"EXAMPLE.COM" fail; a mixed-case ending such as ".Com" is NOT matched).
   Bypasses ("h t t p", "example [kropka] com") are deliberately not detected.
7. OK -> `text`.
`chatMessageLength(text)` (client counter) = number of code points of `NFKC(text)` with ASCII spaces trimmed.
Rejection sentences (PL, also in `chat.rejection.*` of the catalog; the server `message` and `fieldErrors.text[0]` use these PL strings): `not_text` "Wiadomość musi być tekstem.", `empty` "Wpisz wiadomość.", `too_long` "Wiadomość jest za długa.", `control_char` "Wiadomość nie może zawierać znaków sterujących ani nowych linii.", `invisible_char` "Wiadomość nie może zawierać niewidocznych znaków.", `combining_run` "Wiadomość zawiera zbyt wiele znaków łączących.", `url` "Wiadomość nie może zawierać adresów internetowych.".
Test vectors worth porting: lengths 0/1/200/201; "™" -> "TM"; U+FDFA expands to 18 code points (so a 11+ copies exceed 200 although raw < 1000); emoji `👨‍👩‍👧` allowed, ZWJ at edges refused; RTL Hebrew/Arabic allowed; U+202E, U+2066..U+2069, U+200B, U+FEFF -> `invisible_char`; U+2800 -> `invisible_char`; "\u0000" and "\n" -> `control_char`; 4 combining marks ok, 5 -> `combining_run`; `<script>alert(1)</script>` is ACCEPTED (stored/rendered as text; it has no `://`); `javascript:alert(1)` refused; `http://x`, `www.x.pl`, `1.2.3.4`, `ok.com`, `a。com` refused; "1.5", "ok…", "Dobra.Gramy" pass.

### 2.3 Chat state (`deriveChatState`, `deriveSpectatorChatState`, `core/chat/state.ts`)

```
deriveChatState({status, windowOpen, mine, theirs, isPublic}):
  waiting | cancelled                      -> "unavailable"
  finished and !windowOpen                 -> "closed"
  !mine                                    -> "disabled_by_you"
  theirs === false and !isPublic           -> "disabled_by_opponent"
  otherwise                                -> "open"
service.stateOf(context): if `gone` (deleted-account seat) -> "unavailable" (checked BEFORE deriveChatState)
deriveSpectatorChatState({status, windowOpen}):
  waiting | cancelled -> "unavailable"; finished and !windowOpen -> "closed"; else "open"
```
- `windowOpen` = `g.status = 'finished' and g.finished_at > now() - 1 h` computed in SQL (DB clock).
- `mine` = the asker's `chat_enabled`; `theirs` = the OTHER seat's `chat_enabled` (NULL when there is no second player, then status is `waiting` anyway).
- In a PUBLIC game (`is_public`, i.e. kill-switch not pulled) the other player's switch never makes the state `disabled_by_opponent`: it stays `open` (the asker can still write to the spectators) and `read` adds `opponentDisabled: true` (only when `state == open && is_public && theirs === false`). Your own switch still wins (`disabled_by_you`). After the kill-switch (`is_public = false`) the private rule applies again.
- A spectator has no switch: players' settings never touch the spectator chat.

State matrix for private games (mine, theirs) -> I see / opponent sees: (on,on)=open/open; (off,on)=disabled_by_you (no messages) / disabled_by_opponent (history visible, cannot write); (on,off)=disabled_by_opponent / disabled_by_you; (off,off)=disabled_by_you / disabled_by_you. A player who disabled does not learn whether the other disabled too until they enable.

### 2.4 Service logic

One service for reading and writing; SQL below is the old shape (parameters bound, no interpolation; keep DB time).

Context (one row for the asker, the game and the other seat) - `p.id = :playerId and g.id = :gameId` (a mismatch or a vanished game = `404 NOT_FOUND` "Nie znaleziono partii."):
```sql
select p.id as sender_id, p.seat, p.chat_enabled as mine, o.chat_enabled as theirs,
  g.status, g.is_public,
  exists (select 1 from game_players d where d.game_id = g.id and d.kind = 'account' and d.user_id is null) as gone,
  (g.status = 'finished' and g.finished_at > now() - (:retention_ms * interval '1 millisecond')) as window_open,
  (select extract(epoch from clock_timestamp() - max(m.created_at)) * 1000
     from chat_messages m where m.sender_id = p.id)::float8 as since_last_ms,
  (select count(*) from chat_messages m where m.game_id = g.id)::int as total
from game_players p join games g on g.id = p.game_id
left join game_players o on o.game_id = p.game_id and o.id <> p.id
where p.id = :player and g.id = :game
```
Message projection: `m.seq, p.seat (left join game_players p on p.id = m.sender_id), m.author_name, m.body, to_char(m.created_at at time zone 'UTC','YYYY-MM-DD"T"HH24:MI:SS.MS"Z"') as created_at`. Pages:
- after cursor: `... where m.game_id = :g and m.seq > :after order by m.seq limit :limit`;
- latest: `select * from (... where m.game_id = :g order by m.seq desc limit :limit) latest order by seq`.
`retryAfterMs(sinceLastMs, minIntervalMs) = null -> 0; else max(0, ceil(minIntervalMs - sinceLastMs))`.

**read(participant, gameId, {afterId?, limit})**: context -> state. Messages are returned ONLY when state is `open` or `disabled_by_opponent` (`disabled_by_you`, `unavailable`, `closed` -> `[]`). `retryAfterMs` only when `state == open` and > 0. `lastId = last message id or afterId or 0`. `limits = { maxLength, minIntervalMs }` of the human config. No writes.

**send(participant, gameId, {text, clientId})** (checks in this order):
1. (route) body schema, then participant, then
2. `kind` lookup of the player row (`404` if gone), `normalizeChatMessage(text, human maxLength)`; a refusal -> `400 VALIDATION` (2.6).
3. ONE transaction: `select pg_advisory_xact_lock(hashtextextended(:gameId::text, 0))` (serializes sends, setting changes and `seq` allocation of that game; a key of its own, distinct from the spectator-join lock).
4. context; then REPEAT: `select ... where m.sender_id = :player and m.client_id = :clientId` -> if found return it (`200`, `created = false`, `retryAfterMs` = current wait, NO state/limit/interval checks, nothing written).
5. state: `unavailable | closed` -> `409 CHAT_UNAVAILABLE`; `disabled_by_you | disabled_by_opponent` -> `409 CHAT_DISABLED`.
6. `total >= maxMessagesPerGame` -> `409 CHAT_FULL`.
7. `wait = retryAfterMs(since_last_ms)`; `> 0` -> `429 RATE_LIMITED`, header `Retry-After = ceil(wait/1000)`, `error.data = { retryAfterMs: wait, reason: "chat_interval" }`.
8. `insert into chat_messages (game_id, seq, sender_id, client_id, body, created_at) values (:g, (select coalesce(max(seq),0)+1 from chat_messages where game_id = :g), :player, :clientId, :text, clock_timestamp())`, then re-select the row by `(sender_id, client_id)`.
9. Result `{ message, retryAfterMs: minIntervalMs (the full interval), created: true }` -> HTTP `201`.
A foreign-key violation (the game/player vanished under us through cleanup) -> `404 NOT_FOUND`, never `500`.

### 2.5 `PUT /api/games/{id}/chat/settings`

- Caller: participant (account or guest). CSRF. Body strict `{ "enabled": boolean }` (anything else - string, number, null, missing, extra field - `400 VALIDATION`, message "Ustawienie czatu musi być wartością logiczną.").
- Order: CSRF 403 -> body 400 -> participant 404 -> service. Transaction under the same advisory lock as `send`; context; state BEFORE the change: `unavailable | closed` -> `409 CHAT_UNAVAILABLE` ("Czat jest teraz niedostępny w tej partii."); if `mine != enabled`: `update game_players set chat_enabled = :enabled where id = :player` (a repeat of the current value writes nothing and is `200`); returns `{ state }` = the state AFTER the change as the asker sees it (`open` | `disabled_by_you` | `disabled_by_opponent`).
- Allowed from the first moment the panel shows a chat (no "after first message" condition). No confirmation dialog, no rate limit of its own, no persistence beyond the game row.
- Response `200 { "ok": true, "data": { "state": "disabled_by_you" } }`, `no-store`.
- `404` for non-participants/unknown games (uniform). FK violation -> `404`.

### 2.6 `GET /api/games/{id}/chat` and `POST /api/games/{id}/chat`

**GET** `?after_id=N&limit=M` (no CSRF). Query schema: `after_id` string `^\d{1,10}$` then number `<= 2147483647` (optional; else `400 VALIDATION`, message "Nieprawidłowy parametr after_id."), `limit` string `^\d{1,3}$`, 1..100, default 50 (else "Nieprawidłowy parametr limit."). Order: query 400 -> participant 404 -> service. The query is validated BEFORE the participant (a bad `after_id` on any id gives 400).
`200`:
```jsonc
{ "ok": true, "data": {
  "state": "open" | "disabled_by_you" | "disabled_by_opponent" | "unavailable" | "closed",
  "messages": [ { "id": 7, "seat": 1 | 2 | null, "spectatorName"?: "Kuba", "text": "hej", "createdAt": "2026-11-22T10:00:00.123Z" } ],   // ascending by id
  "lastId": 7,
  "limits": { "maxLength": 200, "minIntervalMs": 2000 },
  "retryAfterMs"?: 1200,          // only state == open and the asker is within the interval
  "opponentDisabled"?: true       // only open + public game + the other player turned it off
} }
```
`id` = `seq`. `seat` is `null` exactly for a spectator's message (then `spectatorName` present, a player's message has no `spectatorName`). Field set is exact: no `user_id`, e-mail, client id. `Cache-Control: no-store`. `after_id` above the max id -> empty list (not an error); no `after_id` -> the latest `limit`.

**POST** body `{ "text": string, "clientId": uuid }`, strict (unknown field -> `400`), `text` max 1000 UTF-16 units ("Wiadomość jest za długa."), `clientId` uuid ("Nieprawidłowy identyfikator wiadomości."). Order: CSRF 403 -> body (invalid JSON / schema) 400 -> participant 404 -> service (2.4).
Results:
| HTTP | code | when | notes |
| --- | --- | --- | --- |
| 201 | - | new message | `data = { message: {id, seat, text, createdAt}, retryAfterMs }` |
| 200 | - | repeat of the same `clientId` | same shape; no limit spent, no duplicate; also after the chat state changed |
| 400 | `VALIDATION` | refused text | `error.message` = the PL rejection sentence; `fieldErrors: { text: [sentence] }`; `fieldIssues: { text: [{ code: "CHAT_REJECTED", params: { reason } }] }`; `error.data = { reason }`. ### 3.5 Closing the audience (kill-switch, E10-S05, BR-43) - `POST /api/games/{id}/audience/close`
- Caller: the CREATOR (seat 1, account or guest). CSRF. No body.
- Order: CSRF 403 -> participant 404 -> service. Service transaction: `count(game_players where id = :player and game_id = :g and seat = 1)` = 0 -> `404 NOT_FOUND` (seat 2 and strangers alike); `select status, is_public, audience_closed_at is not null as closed from games where id = ? for update` (row lock; none -> 404);
  - if NOT yet closed: `status` not in (`active`,`finished`) -> `409 GAME_NOT_ACTIVE` with `data.reason = "audience_not_closable"` ("Publiczność można zamknąć tylko w trwającej albo zakończonej partii."); `!is_public` -> `409 GAME_NOT_PUBLIC` ("Ta partia nie jest publiczna."); else `update games set is_public = false, audience_closed_at = :now where id = ?` and `delete from chat_messages where game_id = ? and spectator_id is not null` (what the spectators wrote leaves the players' chat);
  - then return the creator's GameView built in the same transaction (3.3: `audience` gone, `audienceClosed: true`, no `canCloseAudience`).
- Idempotent: a second call (already closed) = `200` with the state, no writes (the status check is skipped when closed). No reopening exists. For a guest creator the guest cookie is refreshed (sliding).
- Effects: spectators are cut off at their next read (`410 AUDIENCE_CLOSED`, 4.4); spectator rows are NOT deleted (cleanup sweeps them); the code stops opening watching (`410 INVALID_INVITATION`, the join re-checks `is_public` under its lock) and review by code (`404`); the game goes on as private (moves, players' chat continue, the chat rules revert to the private ones, 2.3); `QR` for the game disappears (6).
- UI (`CloseAudience`, rendered in the board screen under the public flag): only when `canCloseAudience`: secondary button `game.audience.close` (`data-testid="close-audience"`) opening a confirm dialog: title `game.audience.closeTitle`, body `game.audience.closeBody` (irreversible), confirm `game.audience.close` (`game.audience.closing` while sending; `shared.retry` after an error), cancel `game.audience.keep`; closing the dialog is blocked while sending; errors in a `role="alert"` line above the body: `GAME_NOT_ACTIVE|GAME_NOT_PUBLIC` -> `game.audience.notClosable` + refresh; `network` -> `game.shared.network` text; other -> `game.audience.closeFailed`; `NOT_FOUND` -> gone. On success the answer replaces the room state (`after = 0`). When `audienceClosed` both players see `role="status"` paragraph `game.audience.closedNote` (`data-testid="audience-closed-note"`). Double-click guarded.

## 4. Spectators (E10-S02, S03)

A spectator is neither a participant nor a guest: no `game_players` row, no seat, no history (BR-24), no BR-13 slot. They can only read the state and the chat of one public game and write chat messages. Every player route (`resolveParticipant`) treats a spectator as a stranger (`404`); every spectator route treats a player as a stranger, EXCEPT the game page and the QR route that try the player first, then the spectator.

### 4.1 `POST /api/invitations/{code}/spectate` - become a spectator
- Caller: anyone (account by session, visitor by the spectator cookie). CSRF. Body optional (`{}` when absent): `{ "nickname"?: string }` with the F3 nickname rules (`nicknameSchema`: NFC, control chars -> space, Cf dropped except ZWNJ/ZWJ, space separators collapsed, trim; 1..24 code points of letters/marks/digits/space/`_`/`-`, reserved names refused; empty after normalization = absent). Errors in `fieldErrors.nickname` / `fieldIssues.nickname` with `NICKNAME_*` codes as in F3.
- Order: CSRF 403 -> body schema 400 -> current account (session) -> service:
  1. an account with a `nickname` given (not empty) -> `400 VALIDATION` `fieldIssues.nickname = [{code:"NICKNAME_GUEST_ONLY"}]` ("Nick podaje tylko gość."), BEFORE the pool;
  2. `withLookupAttempt` (pool hit before; release on success and on non-410 errors, kept on `410`);
  3. `normalizeInvitationCode` (none -> uniform `410 INVALID_INVITATION`);
  4. a visitor's fresh token is created BEFORE the transaction (accounts have none); transaction: `select g.id, g.status, g.is_public from invitations i join games g ... where i.code = ?` (none -> `410`); `pg_advisory_xact_lock(hashtextextended('spectate:' || gameId, 0))` (own key); re-read the game: `status <> 'active'` or `!is_public` -> `410 INVALID_INVITATION` (never joinable while `waiting`: the first person with the code becomes the opponent as before, BR-39);
  5. account who PLAYS in this game (`select 1 from game_players where game_id = ? and user_id = ?`) -> return `{ gameId }`, nothing written (they are a player, not a spectator);
  6. returning spectator: existing row of the account (`game_id, user_id`) or of the cookie token (`game_id, token_hash`), alive OR expired -> slide (`last_seen_at = now`, `expires_at = now + 1 h`) and return `{ gameId }` WITHOUT counting against the limit and without a new cookie;
  7. otherwise count present spectators (`COUNT_PRESENT_SQL`); `>= 20` -> `409 SPECTATORS_FULL` ("Partia ma komplet widzów"; the client text is `errors.api.SPECTATORS_FULL` / `home.watch.fullTitle`);
  8. insert (`user_id` for accounts else NULL; `nickname` only for a visitor, else NULL; `token_hash` for a visitor, `created_at = last_seen_at = now`, `expires_at = now + 1 h`).
- Success `200 { "ok": true, "data": { "gameId": "<uuid>" } }`; a NEW visitor gets `Set-Cookie` (spectator cookie, 3600 s) - the token is never in the JSON; a returning visitor keeps their cookie; accounts get none. A visitor who already carries a cookie of an old, deleted row gets a fresh token (no row matches, so a new row and cookie).
- Errors: `400 VALIDATION`, `409 SPECTATORS_FULL`, `410 INVALID_INVITATION` (unknown, malformed, private, closed audience, not `active`: waiting/finished/cancelled), `429 RATE_LIMITED` (pool), `403` CSRF.

### 4.2 Identity resolution (`resolveSpectator(gameId)`)
`gameId` must parse as a UUID (else `404`); then `SpectatorService.find({userId?, tokenHash?}, gameId)`: account row first (`game_id = ? and user_id = ? and expires_at > now`), then token row (`game_id = ? and token_hash = ? and expires_at > now`); none -> `404 NOT_FOUND` "Nie znaleziono partii." (same answer for no game / not a spectator / expired). Result `{ spectatorId }`. (A signed-in account that also has a token cookie: the account row wins; if it has no row but the cookie matches, the token row is used.)

### 4.3 `GET /api/games/{id}/spectate?after=N` - state for a spectator
- Query `after` as F3 5.2 (`^\d{1,5}$`, default 0; validated BEFORE the spectator is resolved; `after > moveCount` -> `400` "Nieprawidłowy parametr after." from inside the service, which rolls back the slide).
- Transaction: (a) `select last_seen_at <= :now - 10 s as stale, (nickname is not null or user_id is not null) as can_chat from game_spectators where id = ? and game_id = ? and expires_at > :now` (none -> `404`); if `stale`: `update game_spectators set last_seen_at = :now, expires_at = :now + 1 h`; (b) the F3 lazy loss on time `settleExpired(gameId, tx, now)` (the only change a spectator's read can make to a game; no lazy cancellation, no `seen_at`); (c) load the game (vanished = `404`); (d) `!is_public` -> `410 GONE` code `AUDIENCE_CLOSED` ("Twórca zamknął publiczność tej partii.") - thrown inside the transaction, so the slide of (a) is rolled back; (e) players ordered by seat; board view with `after`; clock view; `audience` (3.3 rule); `canChat`.
- Response `200 data` (camelCase, dates ISO ms UTC) = the F3 GameView WITHOUT `you`, `invitation`, `closedReason`, `rematch`, `fromRematch`, and with `players[]` WITHOUT `seen`:
```jsonc
{ "status": "active" | "finished" | "cancelled", "variant": "classic", "timeControlMs": 600000,
  "moveCount": 12, "blackSeat": 1|2|null, "turnSeat": 1|2|null, "moves": [..after the first N..],
  "result": null | { "winnerSeat", "reason", "winLine" },
  "clock": { "remainingMs": [a, b], "running": 1|2|null, "now": 1763800000000 },
  "players": [ { "seat": 1, "kind": "account"|"guest", "displayName": "Ala" | "Gracz 2" | null } ],
  "audience"?: { "spectators": 3 },        // active + public only
  "canChat": true,                         // the spectator has a nickname or an account
  "finishedAt"?: "ISO"                     // only finished
}
```
No code, no tokens, no e-mail, no `seen`, no rematch, no chat settings. A `finished` game stays readable while the spectator's access lasts; a `cancelled` one reads too (it can happen if the creator never opened the page within 15 min - the spectator screen shows the cancelled notice).
- After a successful read the route re-sets the spectator cookie with `Max-Age 3600` when the browser carries one (sliding); accounts have no cookie. `Cache-Control: no-store`. Not CSRF (GET). NOTE: only THIS route slides the access; the spectator chat routes do not.

### 4.4 Game page `/games/{gameId}` decision order (F3 page + F4)
1. `loadGameView(gameId)` (F3: participant resolution, marks `seen_at`) -> player room (F3, with the F4 additions of section 9).
2. Not a participant -> spectator: `resolveSpectator` + the state read of 4.3 (this IS a state read: it slides the access). `404` page (GameGate) for "not a spectator / no such game / expired access"; `AUDIENCE_CLOSED` -> the closed screen (HTTP 200, `data-testid="audience-closed"`: `ErrorState` title `game.audience.closedTitle`, body `game.audience.closedBody`, link `/` with `game.shared.backHome`); else the spectator room with the initial view.
A visitor who is neither: 404 page (F3).

### 4.5 Spectator room (`SpectatorRoom`, read-only)
Layout order: `h1` (`game.spectator.watching` while active, `game.shared.finishedHeading` when finished), info alert `game.spectator.youWatch`, public flag (3.3), poll status (not finished: 1-2 failures `role="status"` `game.shared.pollRetry` {attempt},{max=3}; >= 3 danger alert `game.shared.pollFailed` with `game.shared.checkNow`), result banner (finished; neutral outcome of 3.4) or turn status (`game.spectator.turn` {side}=`game.sides.classic.genitive.{colour}`, {name}= label of the seat on turn; coloured stone marker), clocks black first then white (name = `game.spectator.sideName` {side}=`game.sides.classic.title.{colour}` followed by `PlayerLabel`; the running one is `active` with label `game.spectator.clock`; clock rendering/countdown identical to F3 `useGameClock`, `onExpire` = poll at once), the read-only board (F3 board with `readOnly`, `aria-label` `game.shared.boardLabel`, last move and winning line shown), the QR panel (6.2), the spectator chat (4.6), link `/` `game.shared.backHome`.
Special screens: `gone` (a read gave `404`): error state title `game.spectator.goneTitle`, body `game.spectator.goneBody`, link `/join` `game.spectator.goneLink`; `closed` (a read gave `AUDIENCE_CLOSED`): the closed screen of 4.4; `cancelled`: `h1 game.shared.cancelledHeading`, warning `game.spectator.cancelled`, link home.
Polling: `GET /spectate?after={moves known}` merged with the F3 `mergeState` rule; every 2000 ms; after 60 000 ms (monotonic clock) without a new `moveCount` every 5000 ms; ONLY while `status == active`, not hidden, not gone, not closed (a finished/cancelled game is not read again: the last answer carried the result); on return from a hidden tab (and not gone/finished) reschedule and read at once; each read has an 8 s timeout (a hung read counts as a failure); one read in flight; failures counter reset on success.

### 4.6 Spectator chat
Routes (resolution by `resolveSpectator`; players' chat routes know no spectator, so `404`; there is NO settings route for spectators):
- `GET /api/games/{id}/spectate/chat?after_id&limit` - same query rules and same `ChatReadData` JSON as 2.6, from EVERY sender; `state` is `open` | `closed` | `unavailable` (never `disabled_*`: the players' switches do not hide anything from a spectator); `limits` = human limits; `retryAfterMs` = the spectator's own interval; never `opponentDisabled`. Messages only when `open`. Order: query 400 -> spectator 404 -> service.
- `POST /api/games/{id}/spectate/chat` body `{ text, clientId }` (same schema as 2.6). Order: CSRF -> body 400 -> spectator 404 -> service: text normalization (human max length) -> `400` with the same `fieldErrors/fieldIssues/data.reason` -> transaction with the SAME per-game advisory lock as the players' send -> spectator context (below; none = `404`) -> `name IS NULL` (a visitor without a nickname, no account) -> `403 FORBIDDEN` `data.reason = "spectator_name_required"` ("Aby pisać na czacie, wejdź z nickiem lub zalogowany jako konto.") - this check comes BEFORE the repeat check -> repeat by `(spectator_id, client_id)` returns the stored message `200` -> state (`deriveSpectatorChatState`): not open -> `409 CHAT_UNAVAILABLE` -> `total >= 500` -> `409 CHAT_FULL` -> interval (`since_last_ms` of THIS spectator) -> `429 RATE_LIMITED` as in 2.4 -> insert `(game_id, seq, spectator_id, author_name = name, client_id, body, clock_timestamp())` -> `201`.
```sql
select s.id as spectator_id, coalesce(s.nickname, u.display_name) as name, g.status,
  (g.status = 'finished' and g.finished_at > now() - (:retention_ms * interval '1 millisecond')) as window_open,
  (select extract(epoch from clock_timestamp() - max(m.created_at)) * 1000 from chat_messages m where m.spectator_id = s.id)::float8 as since_last_ms,
  (select count(*) from chat_messages m where m.game_id = g.id)::int as total
from game_spectators s join games g on g.id = s.game_id left join users u on u.id = s.user_id
where s.id = :spectator and g.id = :game and g.is_public        -- a closed audience = 404 here
```
- Spectators write in the same window as players (active, and finished for 1 h) and under the same text/length/URL/interval/cap rules; their messages are signed `author_name` (the nickname or the account's display name at send time).
- UI `SpectatorChat` (same panel look, `data-testid="chat-panel"`): header with info toggle (note `chat.spectatorInfo`) and collapse button; NO switch; body: skeleton while loading; any state other than `open` -> text `chat.closed`; `open` -> list (own pending bubble named `chat.you` for the spectator) + composer when `canChat`, else the sentence `chat.readOnly` (`data-testid="chat-read-only"`). Spectator messages in any list are labelled "Widz · {name}" (the Node code hard-codes the Polish prefix; use the new key `chat.spectatorLabel`, `data-testid="chat-spectator"`, plain text, wrap anywhere). Player messages are labelled by seat with `PlayerLabel` (name from the state's `players`). Same `useChat` polling (3 s / idle 10 s, 8 s timeout); a `404` from the chat route calls back to re-read the state (this is how "audience closed" vs "expired" is told apart). A polling spectator chat does NOT slide the spectator's access; after the game finished the state polling stops, so the access lapses 1 h after the last state read (then chat reads `404` and the room shows the "gone" screen).
- Players' client behaviour for spectator messages: they appear in the players' list (`seat: null`) labelled "Widz · {name}" and are counted in the "unread" counter of a folded panel (not of mine). After the kill-switch deletes them the cursor-based client keeps already-merged messages until a reload (accepted; gaps in `seq` are normal).

### 4.7 Spectator edge cases
| Case | Behaviour |
| --- | --- |
| First person with the code while the opponent seat is free | becomes the opponent (accept flow), never a spectator |
| Code of a private game / closed audience / not `active` | spectate join `410 INVALID_INVITATION`; the invite page shows `invalid` (private) |
| 21st spectator | `409 SPECTATORS_FULL`; page alert `home.watch.fullTitle` + `home.watch.fullBody` ({count} = 20), status role, no retry loop |
| Returning spectator when the game is "full" | admitted (a row exists, alive or expired), not counted twice |
| Two joins racing for the last place | the advisory lock serializes; exactly one wins |
| Account that plays this game opens the code | treated as a player: `{ gameId }`, no spectator row; the invite page redirects to the game page |
| Spectator tries a move, resign, rematch, player chat, chat settings | `404` (player routes know no spectator); state unchanged |
| Spectator access expired (1 h without a state read) | `404` everywhere; the room shows `gone`; the code re-admits (row exists, is slid) |
| Game ends while watching | last answer carries `result`/`finishedAt`; polling stops; chat stays 1 h |
| Visitor deletes the cookie / other browser | new token, a new row; the old row lingers until cleanup (counts as present only 15 s) |
| Account spectator deletes the account | `game_spectators` row and the spectator's messages cascade-deleted |
| Device clock skew | the clocks count against `clock.now` of the server (F3 `useGameClock`) |
| Guest-only cleanup of the game | rows/messages cascade with the game |

## 5. Cleanup and account deletion (extends F3 section 8; order matters)

New rules, inserted in `CLEANUP_RULES` after `lobbySeekers` and BEFORE `waitingGames` (before every rule that deletes from `games`; so the chat is swept in short batches instead of a heavy cascade inside a game batch). Same engine as F3 (`delete ... where pk in (select pk ... limit 1000 for update skip locked)`, cutoff = now - grace, 15 s budget per rule, one rule's failure does not stop the others). Result JSON gains `chatMessages` and `gameSpectators` (additive).

| key | table | condition (each `?` = the same cutoff) | grace |
| --- | --- | --- | --- |
| `chatMessages` | `chat_messages` | `exists (select 1 from games g where g.id = chat_messages.game_id and ((g.status = 'finished' and g.finished_at < ?) or (g.status = 'cancelled' and g.created_at < ?) or (g.status = 'active' and <GAME_DEADLINE(g)> < ?)))` - THREE `?` | 1 h (`CHAT_RETENTION_MS`; guard test: equals the `guestTokens` grace) |
| `gameSpectators` | `game_spectators` | `expires_at < ?` | 1 h (reads filter on `expires_at`; the margin absorbs clock skew) |

- `<GAME_DEADLINE(g)>` is the F3 classic formula with the table alias `g` (the unqualified column names resolve to `g`): `coalesce(turn_started_at + (case when (case when move_count % 2 = 0 then black_seat else 3 - black_seat end) = 1 then clock_ms_1 else clock_ms_2 end) * interval '1 millisecond', started_at + 900000 * interval '1 millisecond')`. It makes an abandoned `active` game's chat disappear about 1 h after its clock ran out.
- The chat is swept ALSO for games that stay (history of accounts): the game rules never delete those.
- Physically the text lives from 1 h up to about 2 h after the game ends (hourly cron); the READ hides it at exactly 1 h regardless of the cron (window check in SQL).
- Backups: the old project's operational rule is `pg_dump --exclude-table-data=chat_messages` (structure kept, data not) with 5 rotated copies; carry it into the Rust deployment docs. Not code.

Account deletion (extends F3 4.14; F2d `AccountService.delete`): inside the existing transaction, after the `ACTIVE_GAME` check, the deletion of the user's waiting games and the closing of pending rematches, and BEFORE clearing seat names and `delete from users`:
```sql
delete from chat_messages where game_id in (select game_id from game_players where user_id = :user)
```
(the WHOLE conversation of every game the account played, also the opponent's messages; only row locks, so no cycle with the chat's advisory lock). Spectator rows and their messages go through `on delete cascade` of `game_spectators.user_id`. The opponent's chat in a game with a deleted seat becomes `unavailable` (2.1 rule 5).

## 6. Invite QR (D-35, BR-52, BR-53; `research/decisions/2026-11-04-invite-qr-code.md`)

### 6.1 `GET /api/games/{id}/qr`
- Caller: a PLAYER of the game first (`resolveParticipant`, `NotFound` -> try next), then a SPECTATOR (`resolveSpectator`); anybody else `404 NOT_FOUND`. GET (no CSRF), `connection`/dynamic.
- Service: `select g.status, g.is_public, i.code, i.expires_at > :now as alive from invitations i join games g on g.id = i.game_id where i.game_id = ?`; allowed iff `(status = 'waiting' and alive)` (BR-52: the creator's invitation card, before the opponent joins) OR `(status = 'active' and is_public)` (BR-53: a public game in progress, for players and spectators). Otherwise `404` (so the code never outlives its page: a private game after the opponent joined, a finished game, a closed audience, an expired invitation, a game with no invitation row).
- Content: `invitationUrl(APP_ORIGIN or "http://localhost:3000", code)` = `{origin}/invite/ABCD-EFGH`; generated IN the app (never an outside service). SVG document, EC level M, quiet zone 4 modules, fixed `#000000` on `#ffffff` (a QR needs the same contrast in both themes), must scale (viewBox). Writes nothing: reading it is not presence and does not slide a spectator's access.
- Success headers: `Content-Type: image/svg+xml`, `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`. Errors stay the JSON envelope (`apiHandler`).
- No rate limit.

### 6.2 UI
- Waiting screen (creator): the invitation card has a QR slot under the link and code (card 480 px, QR `--layout-width-qr` 200 px wide, `max-w-full`): `<figure>` with `<img src="/api/games/{id}/qr" alt=game.room.qrLabel class="block aspect-square w-full rounded">` and `<figcaption>` `game.room.qrCaption` ("Zeskanuj telefonem, żeby dołączyć."). Rendered ONLY while `audience` is present in the view (so it follows the public flag: hidden for private games, after the game ends and after the kill-switch). The page does not re-read the image on each poll; the browser loads it once while the panel exists.

## 10. Edge cases worth testing

Chat
1. Two senders at once: `seq` 1,2 without gaps/duplicates (advisory lock); cursor never skips under parallel commits.
2. Same `clientId` twice (also after the chat was disabled in between): second is `200` with the stored message, no second row, no interval spent; new text with the same `clientId` is not a new message (repeat wins).
3. Interval: second message within 2000 ms from the same sender -> `429` + `Retry-After` + `retryAfterMs`; the other player/spectator is unaffected; exact boundary by DB clock.
4. 500th message ok, 501st `409 CHAT_FULL` (players + spectators together); a repeat of an existing `clientId` still returns `200` when full.
5. State windows: game finished `finished_at` +/- 1 s around the hour (`closed` after, empty list, `409 CHAT_UNAVAILABLE` on send, settings `409`); `waiting`/`cancelled` -> `unavailable`; `active` where the clock already ran out but nobody settled it -> still open (chat never settles a game); timeout-finished game: window counts from the deadline `finished_at`.
6. Disable matrix (2.3) incl. both off and one re-enabling; history returns on re-enable; disabling before any message; send racing with disable (a message committed before the PUT stays; after -> `409 CHAT_DISABLED`); repeating the same PUT writes nothing.
7. Public game: opponent disabled does not block me (`open` + `opponentDisabled`); my own switch still does; after the kill-switch the private rule returns.

9. Participant gone mid-request (FK): `404`, not `500`. Stranger/unknown/expired-guest game id: uniform `404`; bad UUID id: `404`.
10. `after_id` = 2147483648 -> `400`; `after_id` beyond max id -> empty list; `limit=0|101|x` -> `400`.
11. Text rules (2.2 vectors), `<script>` accepted as text, rendering as text node, RTL isolation, 200 chars without spaces (wraps), emoji ZWJ, zalgo.
12. No text in logs/errors: error JSON for refused text contains no part of it; verify server logs stay clean.
13. Rematch: new game starts with empty chat and both switches on.
Public games / spectators
14. `isPublic` only from `POST /api/games`; lobby/rematch private; non-boolean -> 400; account without body private.
15. Invite page: public + joinable shows `invite-public` before joining; `watch` view only for `active` public games; finished public game redirects to review; private finished game code -> `invalid`; closed audience -> `invalid`/404 review.
16. Spectate join: 20 present spectators fill the game, the 21st gets `409` (and the lookup pool attempt is NOT kept); a spectator silent > 15 s frees a place; returning spectator bypasses the limit; concurrent last place race; player account is not made a spectator; visitor cookie flow (no token in JSON, `Max-Age 3600`, name `__Host-` prefix rule); account + nickname -> `400 NICKNAME_GUEST_ONLY`.

## 11. Gaps, suspected bugs, and decisions the Rust side must make consciously

1. `SpectatorLabel` hard-codes the Polish text "Widz · {name}" (not in the Node catalogs). New key `chat.spectatorLabel` is provided (PL "Widz · {name}", EN "Spectator · {name}", FR "Spectateur · {name}").
2. The chat routes do not slide the spectator's access (only the state read does). After the game ends the state polling stops, so a spectator's chat dies 1 h after their last state read (then `404`/"gone" screen). Keep, or slide in the chat route (more correct, a small deviation).
3. `audience` is computed with the app clock, the chat with the DB clock; both fine, but do not mix inside one comparison.
4. `closeAudience` does not delete `game_spectators` rows, so a closed game's spectators keep their rows until cleanup; the kill-switch relies on the `is_public` check in `getState`/chat/join. Do not "optimize" the check away.
5. A game shows `audience` only while `active`; a finished public game has no flag and no QR (the QR service rule matches) but the code still opens a review until the audience is closed.
6. The old CHAT_AGENT / `with_bot` / `kind = 'agent'` branches are dropped here. Seam to keep: `kind` as a text column; chat limits struct per kind so agents can come back.
7. No CHECK ties `is_public` to `audience_closed_at` or to `origin = 'invite'` in the old schema (deliberate: BR-40 is enforced by code). A CHECK `audience_closed_at is null or not is_public` is safe to add in Rust if desired.
8. The review page for a code has no own rate limit (UUID + code needed); the invite page is the only place that spends the lookup pool.
9. `retryAfterMs` returned by a successful send is the FULL interval (2000) so the client can disable the button only after a 429; a repeat returns the CURRENT remaining wait.
10. A spectator who is an account is named by `users.display_name` at SEND time (stored in `author_name`); a later rename does not change old messages. Display names are <= 24 so `author_name varchar(24)` holds.
11. The invitation preview counts toward the lookup pool even for `watchable`/`reviewable` results (released on success), exactly like the F3 flows.
12. Old Node `unread` plural for PL: `one/few/many/other`; EN has only `one/other`, FR `one/many/other`: the f4 catalogs follow the F3 rule (union of categories, `other` text as the fallback for a missing one).
